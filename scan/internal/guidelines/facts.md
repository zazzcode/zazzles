# Scanner fact codes

These notes own the interpretation of fixed scanner facts. A request receives only the notes for the codes its model_facts name. Text after a code names the exact expression and file the fact is about.

- `scope_express_direct`: Scope is direct Express registrations with syntactically matched earlier middleware and same-route handlers. Matching source bodies or explicit transport/authentication adapter contracts are supplied; unsupported or dynamic chains remain blockers. For this scope the discovery-stage generic middleware_unresolved warning is superseded by the supplied route/middleware context: judge guard effects from those bodies and actual input transformations, and do not invent additional undisclosed middleware. Known express.json/body-parser parsing adapters parse request values and may admit nested JSON objects; they do not enforce an id/email/name field schema or remove query operators from nested fields, and a parser call alone is not a validator.
- `scope_node_framework`: A verified registration and handler of the named Node framework are supplied. Input acquisition, hooks/schema configuration and value transfers are separate from sink semantics. Source-present controls may be judged; absent or unsupported bodies/scopes remain blockers. A schema declaration is not by itself protection.
- `scope_nextjs`: Scope is a verified Next.js file-system entry: an App Router route handler export, a Server Component page, a Server Action or a Pages Router API route, named after the colon. The file path is the registration. Request values come from the Web Request API (searchParams.get, headers.get, cookies.get, await request.json()/text()/formData()) or from route params, which Next.js decodes before the handler sees them; `params` and page `searchParams` are Promises in Next.js 15+. Server Action arguments are attacker-controlled whatever their TypeScript types; TypeScript annotations are not runtime validation. A higher-order auth wrapper (withAuth) or root middleware that redirects or returns 401/403 is authorization context only: it never encodes, parameterizes or validates a destination value and must not make a SQL, path, SSRF or XSS claim protected. Judge only the supplied handler, helper and schema bodies.
- `zod_schema_supplied`: The named validation helper parses the request value with a zod schema whose source is supplied (validation_schema evidence) and returns its parsed data; a guard on result.success decides whether the handler continues. A type-only rule such as z.string() or z.string().optional() checks the type and still admits SQL metacharacters, ../ sequences, URLs and markup; only explicit constraints (regex, enum, uuid, url with an allow-list, numeric coercion) can limit content. A schema's presence alone is never destination protection.
- `sql_multi_statement`: The named better-sqlite3 exec (or pragma) call runs every statement in its SQL text, so an injected `;` can add stacked statements such as DROP or UPDATE.
- `sql_single_statement`: The named better-sqlite3 prepare call compiles exactly one statement and rejects stacked statements; injected text can still change that statement's logic (UNION, OR 1=1, subqueries).
- `browser_navigation_sink`: The named client sink navigates the browser: an assignment to window.location, location.href, location.assign/replace, window.open or a Next.js router.push/replace target. A value that can start the URL can carry a javascript: scheme, which executes script in the page's origin when navigated (DOM XSS); the same flow is also an open redirect. React does not filter location assignments. Only a fixed literal scheme/origin prefix (for example "/" plus an encoded value, or "https://fixed.host/") or a verified scheme/origin check (new URL(v).protocol allow-list, startsWith("/") && !startsWith("//")) prevents it; a truthiness test is not a check.
- `xss_via_fetched_content`: The named sink renders content the server fetched from a request-chosen URL (the linked SSRF destination) and returned in its response. The attacker controls that remote body, so it is an attacker-controlled origin for this rendering path, like a request value.
- `script_reexecution`: The client code clones inserted <script> elements into newly created script elements after assigning HTML, so injected scripts execute; the impact is script execution, not only markup injection.
- `url_scheme_only_test`: Every raw-text URL test in the handler (a regex test or startsWith) fixes only the scheme, such as /^https?:\/\//; it does not limit the destination host and is not a destination restriction.
- `scope_apollo_resolver`: Scope is a verified Apollo schema field and its independently bound resolver invocation. Only args values have external provenance; parent/context/info and parent-result transitions remain unknown. SDL scalar/type/directive names establish neither database safety nor application validation policy.
- `scope_grpc_unary`: Scope is a verified grpc-js unary service/method with an independently bound handler invocation. Only call.request fields have external request provenance; metadata, context and callback roles remain distinct/unknown. Proto3 field types and decoding do not establish database protection or business validation policy.
- `nosql_selector_semantics`: For selector-value operator injection, distinguish an object from a primitive string: Mongo-style operators inside an object are interpreted, while text such as $ne inside a primitive string remains data. A dominating typeof field !== string rejection that returns/throws before the sink excludes object-valued input for that field on the continuing path, provided there is no intervening mutation or bypass. A mere type test without enforcing control flow does not constrain the sink. Evaluate every selector field and path independently; a guard on one field cannot protect another, and a string used as executable $where text has different semantics.
- `conditional_value_paths`: Conditional value expressions and any directly resolved condition helper bodies are supplied. A static path may be judged under an explicit possible configuration precondition; do not require an observed runtime request/configuration. Reject a path if supplied source proves its precondition impossible. Do not report all runtime configurations as vulnerable merely because one supported branch is unsafe.
- `validator_is_email`: A verified immutable validator.isEmail(value) call is a string/email predicate on that argument only (non-string inputs can throw). It does not transform another request field or remove query operators from a sibling password/selector value. A successful predicate must not lend validation or protection to another field.
- `express_transport_adapters`: Verified default method-override()/express-fileupload() or literal-data express-session options are transport/session adapters, not per-field database validators. Default method override changes request method, default upload handling concerns multipart bodies, and session handling supplies session/cookie state. They do not impose a scalar schema on fields of an already parsed JSON body. Custom callbacks, stores, dynamic options, mutated imports and unknown middleware are not covered by this contract.
- `verified_number_call`: The named transformation is a verified unshadowed ECMAScript Number call. ONLY that call result is numeric (including NaN/Infinity) or throws; this guarantee does NOT apply to the original input or other conditional branches. Evaluate each alternative separately. String truncation and newline removal do not make other alternatives numeric and do not remove query-expression operators. Numeric business requirements remain separate.
- `native_hash_hex`: The named native crypto expression returns hexadecimal text [0-9a-f] on normal completion, or throws. Only this expression's output has that alphabet; raw input and sibling alternatives do not inherit it. Trace helper-return and concatenation transfers separately for each input. This does not establish cryptographic strength or business validation and does not parameterize concatenated SQL. Reference: https://nodejs.org/api/crypto.html#hashdigestencoding
- `supported_transfer`: The named supported transfer carries its receiver into the result; judge whether its pattern constrains the value. The transfer is not a validator by itself.
- `output_alternative_numeric`: The named alternative of a conditional output expression produces only a number on normal completion (or throws); the original request text is not its output.
- `output_alternative_unconstrained`: No numeric output guarantee is established for the named alternative of a conditional output expression; assess its actual constraints independently.
- `numeric_output_expression`: Every output alternative of the named exact expression is proven numeric on normal completion. There is no unconstrained text-output sibling branch in this expression. This is a value-type fact, not business validation or approval of executable-string construction; assess the actual database slot separately.

- `vm_not_security_boundary`: Node's vm module executes code in another context and is not a security boundary. Only its code operand is the claim; context object values are data. Reference: https://nodejs.org/api/vm.html
- `code_inside_string_literal`: Request text is interpolated inside a JavaScript string literal in executable code. A quote break-out remains possible unless every path has a verified grammar or appropriate code-literal conversion.
- `sandbox_library_advisory`: The verified evaluator library has the named sandbox escape advisory. Report poor practice and cite that advisory; do not infer an exploit payload or runtime compromise.
- `protocol_relative_path`: A single slash prefix permits //host and /\host destinations in URL resolution. It does not establish same-site navigation.
- `redirect_back_referer`: The verified Express redirect('back') destination comes from request Referer; request-controlled navigation is the claim.
- `redirect_also_xss`: This navigation has a separate XSS claim for active URL schemes. Open redirect and script execution remain independent records, linked by source location.
- `redirect_predicate_bypass`: The scanner's syntax classification of the validator predicates on this destination path finds that they still permit the listed destination forms: backslash_prefix (`\host`), slash_backslash (`/\host`), protocol_relative (`//host`), absolute_url, origin_prefix (a trusted origin without a trailing slash also admits `https://trusted.evil`), parsed_origin_unfixed (a parsed origin compared with no fixed or base origin), checked_operand_differs (the check tests another value), percent_encoded_after_decode (the value is decoded after the check) or reassigned_after_check. While any form is listed, a same-site-relative or parsed-origin restriction is not established for this path.
- `redirect_predicate_excludes`: The validator predicates on every destination path exclude the listed forms. This is a syntax fact about the predicates only; whether they dominate the redirect, reject before it and cover every path is judged separately.
- `redirect_normalization`: The named redirect contract delivers the destination to the browser URL parser: for http(s) a backslash is treated as a slash, so `/\host` and `\\host` can reach another origin; percent-escapes are not decoded by the parser, so `%2f%2f` only matters where the code itself decodes.
- `sql_literal_quote_doubling`: The named operand passes through single-quote doubling (`'` to `''`) and is placed inside a single-quoted SQL string literal for the named dialect (SQLite, PostgreSQL or CockroachDB with standard-conforming strings), which is a literal escape for that operand only. It does not protect other operands, identifier or numeric positions, MySQL backslash escaping, or later concatenation of raw data.
- `numeric_conversion_result`: The named operand of this statement is the result of a numeric conversion, and nothing later changes its text. ONLY that operand is numeric; the original input, other operands and other paths do not inherit it. A numeric result carries no SQL syntax, quoted or not. Numeric business requirements remain separate.
- `escaped_in_quoted_literal`: The named operand passed through the database client's string escape for its connection, nothing later changes its text, and it sits inside a quoted SQL string literal, so it cannot end that literal. That is a literal escape for that operand only. It does not protect other operands, an operand that is not inside quotes, an identifier or a numeric position, and string-built SQL remains a construction practice finding.
- `hash_hex_result`: The named operand is the hexadecimal text [0-9a-f] of a hash call, and nothing later changes it. Only that operand has that alphabet; it carries no quote, delimiter or operator. This does not establish cryptographic strength.
- `constant_sql_bound_values`: The SQL text of this statement is the quoted constant of the program, and every request value reaches the statement only as a bound parameter. A bound parameter is data: it cannot change the statement's syntax, whatever was or was not done to the value before. This is a fact about this statement only. It says nothing about validation, authorization or another statement.
