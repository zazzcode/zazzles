# Scanner fact codes

These notes own the interpretation of fixed scanner facts. A request receives only the notes for the codes its model_facts name. Text after a code names the exact expression and file the fact is about.

- `scope_express_direct`: Scope is direct Express registrations with syntactically matched earlier middleware and same-route handlers. Matching source bodies or explicit transport/authentication adapter contracts are supplied; unsupported or dynamic chains remain blockers. For this scope the discovery-stage generic middleware_unresolved warning is superseded by the supplied route/middleware context: judge guard effects from those bodies and actual input transformations, and do not invent additional undisclosed middleware. Known express.json/body-parser parsing adapters parse request values and may admit nested JSON objects; they do not enforce an id/email/name field schema or remove query operators from nested fields, and a parser call alone is not a validator.
- `scope_node_framework`: A verified registration and handler of the named Node framework are supplied. Input acquisition, hooks/schema configuration and value transfers are separate from sink semantics. Source-present controls may be judged; absent or unsupported bodies/scopes remain blockers. A schema declaration is not by itself protection.
- `scope_apollo_resolver`: Scope is a verified Apollo schema field and its independently bound resolver invocation. Only args values have external provenance; parent/context/info and parent-result transitions remain unknown. SDL scalar/type/directive names establish neither database safety nor application validation policy.
- `scope_grpc_unary`: Scope is a verified grpc-js unary service/method with an independently bound handler invocation. Only call.request fields have external request provenance; metadata, context and callback roles remain distinct/unknown. Proto3 field types and decoding do not establish database protection or business validation policy.
- `nosql_selector_semantics`: For selector-value operator injection, distinguish an object from a primitive string: Mongo-style operators inside an object are interpreted, while text such as $ne inside a primitive string remains data. A dominating typeof field !== string rejection that returns/throws before the sink excludes object-valued input for that field on the continuing path, provided there is no intervening mutation or bypass. A mere type test without enforcing control flow does not constrain the sink. Evaluate every selector field and path independently; a guard on one field cannot protect another, and a string used as executable $where text has different semantics.
- `conditional_value_paths`: Conditional value expressions and any directly resolved condition helper bodies are supplied. A static path may be judged under an explicit possible configuration precondition; do not require an observed runtime request/configuration. Reject a path if supplied source proves its precondition impossible. Do not report all runtime configurations as vulnerable merely because one supported branch is unsafe.
- `validator_is_email`: A verified immutable validator.isEmail(value) call is a string/email predicate on that argument only (non-string inputs can throw). It does not transform another request field or remove query operators from a sibling password/selector value. A successful predicate must not lend validation or protection to another field.
- `express_transport_adapters`: Verified default method-override()/express-fileupload() or literal-data express-session options are transport/session adapters, not per-field database validators. Default method override changes request method, default upload handling concerns multipart bodies, and session handling supplies session/cookie state. They do not impose a scalar schema on fields of an already parsed JSON body. Custom callbacks, stores, dynamic options, mutated imports and unknown middleware are not covered by this contract.
- `verified_number_call`: The named transformation is a verified unshadowed ECMAScript Number call. ONLY that call result is numeric (including NaN/Infinity) or throws; this guarantee does NOT apply to the original input or other conditional branches. Evaluate each alternative separately. String truncation and newline removal do not make other alternatives numeric and do not remove query-expression operators. Numeric business requirements remain separate.
- `native_hash_hex`: The named native crypto expression returns hexadecimal text [0-9a-f] on normal completion, or throws. Only this expression's output has that alphabet; raw input and sibling alternatives do not inherit it. Trace helper-return and concatenation transfers separately for each input. This does not establish cryptographic strength or business validation and does not parameterize concatenated SQL. Reference: https://nodejs.org/api/crypto.html#hashdigestencoding
- `supported_transfer`: The named supported transfer carries its receiver into the result; judge whether its pattern constrains the value. The transfer is not a validator by itself.
- `output_alternative_numeric`: The named alternative of a conditional output expression produces only a number on normal completion (or throws); the original request text is not its output.
- `output_alternative_unconstrained`: No numeric output guarantee is established for the named alternative of a conditional output expression; assess its actual constraints independently.
- `numeric_output_expression`: Every output alternative of the named exact expression is proven numeric on normal completion. There is no unconstrained text-output sibling branch in this expression. This is a value-type fact, not business validation or approval of executable-string construction; assess the actual database slot separately.
